# llama.cpp Vulkan port

Native, single-application Unikraft images that build upstream **ggml-vulkan**
in-tree and dispatch through the VOGUE Vulkan stack:

```text
llama.cpp / ggml-vulkan -> libvulkan -> libukvulkan_venus -> libukvirtio_gpu -> QEMU Venus
```

Bench and server modes are separate images with direct entrypoints — no shell,
`fork()`, or `exec()`. Local-model only: the appliance always reads
`/mnt/model/model.gguf` and never downloads from Hugging Face or a URL.

```sh
make llama-vk-run        ARCH=x86_64 MODEL=/path/to/model.gguf   # bench
make llama-vk-server-run ARCH=x86_64 MODEL=/path/to/model.gguf   # HTTP server
```

Results go to `results/llama/llama_vk*.json` and `llama_server_vk*.json` (the
server capture also records readiness + HTTP behavior). `make deps` populates the
repo-local `llama.cpp` and Vulkan-header checkouts used by the build.

## Build prerequisites

The SPIR-V shaders are generated by a host cmake cross-build:

```sh
make llama-vk-prepare ARCH=<arch>   # needs a host Vulkan SDK (glslc); writes build-unikraft-vk-<arch>/
```

## Unikraft build notes

The same Unikraft-specific concerns as the CPU port apply (see
[`../app-llama-cpu/PORTING.md`](../app-llama-cpu/PORTING.md)): basename-collision
`|variant` tags, the renamed app entry (`llama-vk-server-entry.cpp`), and a
raised `CONFIG_STACK_SIZE_PAGE_ORDER` (9 / 2 MiB) — the VK path has extra stack
pressure from ggml-vulkan's async pipeline-compile workers. arm64 Kraftfiles also
select `CONFIG_LIBUKINTCTLR_GICV2`.
