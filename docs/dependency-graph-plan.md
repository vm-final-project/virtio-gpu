# VirtIO-GPU Dependency Graph — Implementation Plan

> Status: **executed** — artifacts D1–D5 generated by `make depgraph` into
> `results/depgraph/` (see `results/depgraph/README.md`). This document remains
> the design rationale. Scope: draw the virtio-gpu dependency
> graph across **three codebases and one protocol seam**: the Linux guest driver
> (`../linux/drivers/gpu/drm/virtio`), our Unikraft project *VOGUE*
> (`virtio-gpu/`, a.k.a. the vm-final-project), and the QEMU device model
> (`../qemu-src/hw/display`). This document is code-grounded: every edge claimed
> here was extracted from the checked-out sources (see §7 Evidence). It defines
> *what* to draw, *how* to extract it deterministically, *which* tools to use,
> and *the views* that carry the insight — it does not itself emit the graphs.

---

## 1. Goal & deliverables

Produce a reproducible, governance-checkable set of dependency graphs that make
one thesis legible at a glance:

> **VOGUE replaces Linux's DRM/KMS/GEM subsystem tower with a thin static
> dispatch stack, while keeping the *exact same* VirtIO-GPU + Venus wire
> contract that QEMU + virglrenderer speak on the host.**

Deliverables (artifacts to be created when this plan is executed):

| ID | Artifact | Path |
|----|----------|------|
| D1 | Canonical edge dataset (one normalized CSV/JSON of all edges) | `results/depgraph/edges.json` |
| D2 | Per-codebase Graphviz `.dot` sources | `results/depgraph/{linux,vogue,qemu}.dot` |
| D3 | The three *insight views* (see §5) as `.dot` + rendered `.svg` | `results/depgraph/view-*.{dot,svg}` |
| D4 | Extractor + renderer script | `scripts/gen_depgraph.py` |
| D5 | Make target `make depgraph` + governance hook | `Makefile`, `config/governance.json` |

Non-goals: a clickable call-graph of every function; importing real DRM/Mesa
into the guest; replacing the existing `docs/ARCHITECTURE.md` prose.

## 2. The three-boundary model (the framing that makes this novel)

Most published virtio-gpu diagrams draw **one** codebase, or a single vertical
"guest → host" arrow stack. The insight this plan operationalizes: the
interesting dependencies are *the ones that cross trust/address-space
boundaries*, and the protocol is the **invariant spine** that all three
codebases are forced to agree on.

```
        GUEST                         SEAM                    HYPERVISOR / HOST
 ┌──────────────────────┐   ┌────────────────────────┐   ┌──────────────────────┐
 │ Linux: DRM/KMS/GEM    │   │  VirtIO-GPU virtqueues │   │ QEMU virtio-gpu-*.c   │
 │ tower (13 objs)       │──▶│  control/cursor + Venus│◀──│ + virglrenderer       │
 │  --- vs ---           │   │  ring (the contract)   │   │ + (host) Venus/Vulkan │
 │ VOGUE: libuk* dispatch│──▶│                        │   │                       │
 └──────────────────────┘   └────────────────────────┘   └──────────────────────┘
```

We model the system as a **directed multigraph** `G = (V, E)` where each edge
carries a **kind** label, because "depends on" means three different things and
conflating them is the usual diagram failure:

- **`build`** — wired together at build time. Source of truth differs per repo:
  Kconfig `select`/`depends` (Linux + Unikraft `Config.uk`), `Makefile.uk`
  object/library lists (VOGUE), `meson.build` `source_set` `when:` guards (QEMU).
- **`compile`** — `#include` reachability (header → translation unit).
- **`runtime`** — virtqueue command / ring-message flow at execution time
  (cannot be read from `#include`s; derived from the protocol + code reading).

These three are rendered as distinct edge styles (solid / dashed / bold-colored)
so a single picture can answer "linked, or merely included, or actually talks at
runtime?".

## 3. Nodes & boundaries to capture

**Guest — Linux** (`../linux/drivers/gpu/drm/virtio`, `CONFIG_DRM_VIRTIO_GPU`):
13 objects linked into `virtio-gpu.ko` (from `Makefile`): `virtgpu_drv`,
`virtgpu_kms`, `virtgpu_gem`, `virtgpu_vram`, `virtgpu_display`, `virtgpu_vq`,
`virtgpu_fence`, `virtgpu_object`, `virtgpu_debugfs`, `virtgpu_plane`,
`virtgpu_ioctl`, `virtgpu_prime`, `virtgpu_submit` (+`virtgpu_trace_points`).
External subsystem nodes pulled in by `Kconfig select`: `DRM`, `DRM_KMS_HELPER`,
`DRM_GEM_SHMEM_HELPER`, `VIRTIO`, `VIRTIO_DMA_SHARED_BUFFER`, `DRM_CLIENT_SELECTION`.
The transport node is `virtgpu_vq.c` (includes `linux/virtio_ring.h`,
`virtio_config.h`).

**Guest — VOGUE** (`virtio-gpu/libs/*`): 11 first-party libs — `libukvirtio_gpu`
(frontend + virgl encoder), `libukvirtgpu_drm`, `libukvenus`, `libukvk_icd`,
`libukggml_vk`, `libukdma`, `libukdma_pool`, `libukdrm_compat`, `libukgbm_compat`,
`libukegl`, `libukswrender`. External Unikraft core nodes referenced via
`Config.uk select`: `VIRTIO_DEVICE`, `LIBVIRTIO_BUS`, `LIBUKSGLIST`,
`LIBUKALLOC`, `LIBMUSL`. App sinks: `app-llama-upstream-vk`, `app-kmscube`,
`app-glmark2`, `app-vulkan-smoke`, `app-vkmark`.

**Hypervisor — QEMU** (`../qemu-src/hw/display`): `virtio-gpu-base`, `virtio-gpu`,
`virtio-gpu-gl`, `virtio-gpu-virgl`, `virtio-gpu-pci`, `virtio-gpu-pci-gl`,
`virtio-gpu-rutabaga`, `virtio-gpu-pci-rutabaga`, `virtio-gpu-udmabuf(+stubs)`.
External nodes: `virglrenderer` (lib), `rutabaga_gfx_ffi`, `pixman`, `edid`,
QEMU `virtio-bus`/`virtio.h`.

**Seam (shared contract) — the spine node set:** VirtIO-GPU control/cursor
queues + `VIRTIO_GPU_CMD_*` opcodes, and the Venus command ring. This is the
only node-set that appears in all three columns; it is what makes the
cross-boundary edges *legitimate* rather than cosmetic.

## 4. Extraction methodology (deterministic, per edge-kind)

The extractor `scripts/gen_depgraph.py` emits D1 (`edges.json`) by running these,
in order, each producing `{src, dst, kind, repo}` records:

### 4a. `build` edges
- **Linux Kconfig:** parse `Kconfig` for `select`/`depends on` under
  `config DRM_VIRTIO_GPU*`; parse `Makefile` `virtio-gpu-y :=` for the object
  membership edges (object → module).
- **VOGUE Config.uk:** parse each `libs/*/Config.uk` for `select`/`depends on`
  (already extracted — see §7). Map `LIBUK*` symbols back to lib directories.
- **QEMU meson:** parse `hw/display/meson.build` `*_ss.add(when:[...], if_true:
  files(...))` to get (source → module, gated-by condition) and the
  `virgl`/`opengl`/`rutabaga` feature guards. Optionally cross-check with
  `meson introspect --targets` if a configured build tree exists
  (`qemu-src/build/` is present).

### 4b. `compile` edges
- Preferred (precise, follows the real search path): `clang -M -MG` or
  `gcc -H` per translation unit with each project's real include flags, then
  filter to in-scope headers. For Linux this needs kernel `KBUILD` flags; for
  VOGUE reuse the toolchain include dirs from `cmake/unikraft-clang.cmake` and
  `config/external_paths.json`.
- Fallback (no toolchain needed, fully deterministic, good enough for the
  subsystem view): regex `#include` scan + a header→owning-lib resolver. This is
  what produced the §7 edges and is the default the script ships with; the
  clang path is an opt-in `--precise` mode.

### 4c. `runtime` edges
Not machine-extractable from includes. Encode as a small **curated, cited**
table inside the script (`RUNTIME_EDGES`), each row annotated with the
source file + symbol that justifies it (e.g. the virtqueue `kick`/`add_buf`
site in `libukvirtio_gpu`, the Venus ring submit in `libukvenus`). Treating
runtime edges as *reviewed data with citations* rather than guesses is what
keeps the graph honest and governance-checkable.

### 4d. Normalization
All three feed one schema. Node IDs are namespaced (`linux:`, `vogue:`,
`qemu:`, `seam:`) so cross-boundary edges are unambiguous and the three columns
can be laid out with Graphviz `cluster_*` subgraphs + `rank=same`.

## 5. The graph views (where the "innovated insight" lives)

Rendering the raw multigraph is noise. The value is in three *designed* views,
all generated from the same D1 dataset:

### View A — "The collapse" (comparative subsystem diff)
Side-by-side clusters: **Linux DRM tower** vs **VOGUE dispatch**, both pointing
at the same `seam` spine. Nodes present in Linux but with **no counterpart** in
VOGUE (DRM core, KMS atomic helpers, GEM shmem helper, fbdev, debugfs, the
whole modesetting path for the Vulkan-compute appliance) are colored as
*eliminated dependencies*. This is the headline picture: it quantifies "small
local code" by showing the subgraph VOGUE does **not** depend on. Pair with a
node/edge count delta in the caption.

### View B — "Three views of one edge" (kind-layered)
A single guest→seam→host stack where the **same logical dependency** is drawn
three times with the three edge kinds overlaid (build dashed, compile thin,
runtime bold-colored). Reveals where build wiring and runtime flow *diverge* —
e.g. `libukggml_vk` build-`select`s four libs, but its runtime hot path only
traverses `libukvenus → libukvirtio_gpu → virtqueue`. Surfaces dead-on-the-
hot-path build deps and is genuinely hard to see in code.

### View C — "The invariant spine" (cross-boundary contract map)
Center column = the VirtIO-GPU/Venus protocol opcodes. Left = the guest
producers of each opcode (Linux `virtgpu_vq.c` *and* VOGUE `libukvirtio_gpu`/
`libukvenus`), right = the QEMU consumers (`virtio-gpu.c` dispatch,
`virtio-gpu-virgl.c`, host Venus in virglrenderer). Edges are labeled with the
actual `VIRTIO_GPU_CMD_*` / Venus ring opcode. This proves the seam is a real
shared contract — both guests are interchangeable against the same host — and
doubles as a conformance checklist (any opcode VOGUE emits must have a QEMU
consumer).

Each view is emitted as `.dot` and rendered with `dot -Tsvg` (hierarchical) or
`neato`/`fdp` for the dense subsystem clusters.

## 6. Tooling decision

Canonical format: **Graphviz `.dot`** — text-diffable, scriptable, governance-
checkable, and the lingua franca that the surveyed tools (`cinclude2dot`,
`codeviz`, CMake's `--graphviz`) all target. We generate `.dot` ourselves rather
than adopting `cinclude2dot` wholesale because (a) it only does `compile`-kind
include edges for one tree, and (b) we need the namespaced cross-boundary nodes
and the curated runtime edges it can't know about. We *borrow its model*
(per-file nodes, `--merge module/directory` granularity) and reimplement in
`gen_depgraph.py` so all three edge kinds and all three repos share one path.
A Mermaid (`.mmd`) mirror of Views A/C is optional for inline rendering in
Markdown/the paper.

Reference tools & official docs surveyed (see Sources): Graphviz `dot`/`neato`/
`fdp`; `cinclude2dot` (Perl) and `cinclude2dot2` (Py3) for the include-graph
model; `clang -M`/`gcc -H` for precise include resolution; Kconfig + meson
introspection for build edges; Mesa Venus docs and QEMU virtio-gpu device docs
for the protocol/runtime semantics that justify the §4c runtime edges.

## 7. Evidence — edges already extracted (the plan is grounded, not speculative)

**VOGUE `build` edges (`Config.uk select`/`depends`):**
```
libukdrm_compat   -> libukvirtio_gpu
libukegl          -> libukvirtio_gpu, libukdma, libukswrender, libmusl
libukgbm_compat   -> libukdma
libukggml_vk      -> libukvenus, libukvirtio_gpu, libukvirtgpu_drm, libukvk_icd
libukswrender     -> libmusl
libukvenus        -> libukvirtio_gpu
libukvirtgpu_drm  -> libukvirtio_gpu
libukvirtio_gpu   -> VIRTIO_DEVICE, LIBVIRTIO_BUS, LIBUKSGLIST, LIBUKALLOC  (REAL backend)
libukvk_icd       -> libukvirtgpu_drm
```
**VOGUE `compile` edges (cross-lib `#include <uk/...>`):**
```
libukggml_vk -> uk/venus.h, uk/virtio_gpu.h, uk/drm_virtgpu.h
libukvenus   -> uk/virtio_gpu.h
libukvirtgpu_drm -> uk/virtio_gpu.h, drm/virtgpu_drm.h
libukvk_icd  -> uk/drm_virtgpu.h, uk/virtio_gpu.h, drm/virtgpu_drm.h
libukegl     -> uk/drm_compat.h, uk/gbm_compat.h, uk/swrender.h, uk/virtio_gpu.h
```
**Linux `build`:** `Kconfig` selects `VIRTIO`, `DRM_KMS_HELPER`,
`DRM_GEM_SHMEM_HELPER`, `VIRTIO_DMA_SHARED_BUFFER`, `DRM_CLIENT_SELECTION`;
`Makefile` links the 13 objects above into `virtio-gpu.ko`. **`compile`:**
`virtgpu_drv.h` is the hub (includes `linux/virtio*.h`, `drm/*`, `drm/virtgpu_drm.h`)
included by every `.c`; `virtgpu_vq.c` is the transport (`virtio_ring.h`,
`virtio_config.h`).
**QEMU `build` (`meson.build`):** `virtio-gpu-base.c`+`virtio-gpu.c` gated on
`CONFIG_VIRTIO_GPU`; `virtio-gpu-gl.c`+`virtio-gpu-virgl.c` gated on
`virgl`+`opengl`; rutabaga path gated on `rutabaga`. **`compile`:**
`virtio-gpu-gl.c`/`virtio-gpu-virgl.c` → `<virglrenderer.h>`;
`virtio-gpu-rutabaga.c` → `<rutabaga_gfx/rutabaga_gfx_ffi.h>`; all → `virtio-gpu.h`.

## 8. Implementation steps (execution checklist)

1. **Scaffold** `scripts/gen_depgraph.py` with the §4 extractors; default to the
   regex/`select`/`meson`-parse path (no toolchain needed), `--precise` for clang.
2. **Emit D1** `results/depgraph/edges.json` (namespaced nodes, kind-labeled edges).
3. **Emit D2** per-repo `.dot` and **D3** the three §5 views; render `.svg` via
   `dot`/`neato` (skip-with-warning if Graphviz absent, mirroring the `typst`
   handling in the paper gate).
4. **Curate** the §4c `RUNTIME_EDGES` table with file+symbol citations; reviewed,
   not guessed.
5. **Wire `make depgraph`** + a `depgraph-check` that re-extracts and fails if
   `edges.json` drifts from the committed copy (so the graph can't silently rot).
   Register ownership in `config/governance.json`; run `make governance-check`.
6. **Embed** View A and View C into `docs/ARCHITECTURE.md` and the paper
   (`paper/`), with node/edge-delta captions.
7. **Validate** the seam: assert every `VIRTIO_GPU_CMD_*`/Venus opcode VOGUE
   emits has a QEMU consumer node (View C doubles as the test).

---

## 9. Risks & mitigations

- **Include-scan imprecision** (macro/conditional includes) → offer `--precise`
  clang mode; the subsystem-level view tolerates the regex approximation.
- **Runtime edges drifting from reality** → citation-per-edge + the View-C
  opcode conformance check turns drift into a test failure.
- **Cross-version skew** (Linux/QEMU/virglrenderer pinned versions) → record the
  checkout commit of each sibling in `edges.json` metadata.
- **Graph clutter** → never render the raw multigraph; only the three designed
  views ship.
